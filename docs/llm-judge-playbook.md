# LLM 裁判评估方案（E融助手）

> 适用前提：客服 agent 只做两件事——识别用户意图，然后从**人工写好的答案库**里挑一条发出去。
> 不生成文字、不改写、不拼接。本文所有结论都建立在这个前提上。

---

## 一、先定性：这是选择题，不是作文题

答案的文字是自己写的、事先审过的，所以这些风险在设计层面就已经消失了：

| 常见评估维度 | 在本系统是否适用 | 原因 |
|---|---|---|
| 忠实度 / 有没有编造 | **不适用** | 答案是固定文本，没有编造空间 |
| 合规越界 | **不在运行时** | 写答案库时人工过一遍，一次性永久生效 |
| 偏爱长回答 | **不适用** | 长度由答案库决定，模型无法发挥 |
| 偏爱同门模型 | **不适用** | 没有生成风格可偏袒 |
| 检索 vs 生成归因 | **不适用** | 没有生成环节 |

**结论：安全保障来自答案库本身，不来自裁判。** 结构性保证（能发出去的话都审过）比任何抽查都强一个量级。裁判在这里是体检工具，不是保险丝，粗糙够用即可。

---

## 二、主评估不需要裁判

输出是"选了哪条答案"，所以：

准备一份题库，每道题标注正确答案编号 → 跑一遍 → 对就是对，错就是错。

这个分数是**确定的、免费的、跑一百遍结果一致**的。不存在裁判准不准、要不要校准、有没有偏见的问题。上一版方案里的一致率、kappa、锚点样例，在主流程里全部用不上。

### 盯三个数就够

| 指标 | 定义 | 说明 |
|---|---|---|
| **选对率** | 选中编号 == 标注编号 | 主指标 |
| **该转人工却硬答** | 库里没有合适答案，但系统挑了个最像的发出去 | **最大风险，优先级高于选对率** |
| **易混淆答案对** | 被互相选错次数最多的答案组合 | 最有行动价值 |

第三个数直接指向该动手的地方，而且通常**改答案库**就能解决：内容太接近的两条合并、一条盖了两种情况的拆开、常见说法没覆盖的补进去。杠杆在库上，不在模型上。

### 关于样本量

- 同一版本重跑两次，分数波动多少？先测这个基线，否则后面所有对比都没意义。
- 50 条样本上"从 82% 涨到 85%"大概率是噪声。要判断改动是否真的有效，样本量至少得让这个差值超出波动范围。

## 三、裁判真正的三个用武之地

主流程不用裁判，但下面三处它不可替代。

### 用途 A：扩题库（收益最高，先做这个）

题库是整套评估的唯一资产。从线上真实提问里抽，再让模型扩出同义说法。

```
你是客服质检助手。下面是一条标准问法：

【标准问法】{{question}}

请生成 8 条真实用户可能说出的变体，要求：
- 覆盖口语化、省略主语、带错别字、带情绪、超短（3-5 字）等不同形态
- 语义必须与标准问法完全一致，不要改变意图
- 不要生成书面语、客服腔

直接输出 8 行，每行一条，不要编号和解释。
```

**用法**：挑 30-50 道核心题各扩 8 条，跑一遍看是不是都落到同一条答案。落错的，就是答案库该补说法的地方。

### 用途 B：判"该不该转人工"（最重要的边界）

选择题系统最典型的失败模式：库里其实没有合适答案，系统挑了个最接近的硬答。

```
你是客服质检员。判断这个问题在现有答案库里是否有真正合适的答案。

【用户原话】{{user_query}}

【库中最接近的 3 条候选】
1. {{candidate_1_title}}：{{candidate_1_text}}
2. {{candidate_2_title}}：{{candidate_2_text}}
3. {{candidate_3_title}}：{{candidate_3_text}}

判定标准：
- 有：某条候选能直接、完整地解决用户的问题，用户看完不需要再追问。
- 没有：所有候选都只是话题相关，但没有正面回答用户真正在问的事；
        或用户问的是候选覆盖范围之外的情况。

先写 2-3 句理由，再输出结论。

输出 JSON：
{"reason": "...", "verdict": "有" | "没有", "best_candidate": 1|2|3|null, "confidence": "高"|"低"}
```

**用法**：`verdict` 为"没有"却被系统答了的，就是该转人工没转的案例。`confidence` 为"低"的，全部路由人工复核。

### 用途 C：判模糊题（有多条答案都说得通）

题库里总有些题不止一个正确编号。这类题不能用精确匹配打分，交给裁判：

```
你是客服质检员。判断这条回答是否恰当地回应了用户。

【用户原话】{{user_query}}
【系统选中的答案】{{selected_answer}}

判定标准（三档）：
- 合格：直接回应了用户真正在问的事，场景对得上，用户看完能解决问题。
- 勉强：话题相关且没有误导，但没答到点上，用户大概率还要再问一次。
- 不合格：答非所问，或场景错配（文字本身没问题，但放在这个场合会让用户误解）。

先写 2-3 句理由，再给结论。

输出 JSON：
{"reason": "...", "verdict": "合格"|"勉强"|"不合格", "confidence": "高"|"低"}
```

## 四、写裁判提示词的几条硬规矩

1. **分档越少越稳**。二元或三档，不要用 1-5 分。模型自己都分不清 3 分和 4 分，同一条跑两次能给出不同结果。想要细腻度，靠"理由"那段文字补，不要靠拉长刻度。
2. **先写理由，再给结论**。顺序反了，理由就变成给结论找的借口。
3. **判定标准要写成可判定的条件**，不要写"回答好不好"。上面模板里每一档都有明确的行为描述，照这个密度写。
4. **每档配 2-3 个边界样例**放进提示词。这一步对稳定性的提升，通常比反复雕琢标准文字大得多。尤其要放"合格 vs 勉强"的擦边案例。
5. **输出结构化**，固定 JSON 字段，方便批量统计。加一个 `confidence` 字段做人工复核的路由开关。

### 场景错配：本系统真正要防的那类错误

文字合规、但放错场合。例如用户问贷款相关的事，系统挑了一条讲信用卡的答案——单看文字没问题，放在这个语境里可能被读成给了不该给的建议。

这是金融场景下唯一需要认真对待的残留风险，模板 C 的"不合格"档已经把它写进去了。

## 五、裁判本身的可靠性（按需做，别提前做）

只有当裁判的判定要直接用于自动化决策（比如自动拦截、自动改配置）时，才需要下面这些。如果只是人看的体检报告，跳过。

- **校准**：抽 50-100 条，人工标一遍，跟裁判对一对。
  - 注意：**不要只看原始一致率**。如果九成样本本来就是"合格"，一个无脑全判合格的裁判也能拿九成一致率，但毫无信息量。要么分类别看，要么用扣掉瞎蒙成分的一致性系数（Cohen's kappa）。
  - **上限是人-人一致率**。先让两个同事标同一批，看他俩能达成多少一致。那个数才是裁判的天花板，要求裁判超过它是在拟合噪声。
- **配置固定**：温度设 0，钉死模型版本，提示词打版本号并随每条结果落库。很多时候"分数漂移"漂的不是系统，是裁判——上游模型静默更新一次，历史分数就断层了。
- **回归**：留一份人工标注的金标集，每次改裁判提示词都拿它重跑一遍。裁判提示词就是代码。

### 位置偏见（只在做两两对比时才有）

如果让裁判在两个方案里选优，它会偏向排在前面的那个。破法：两个顺序各跑一次，结论不一致的判为**平局**（不是作废）。不一致率本身就是裁判健康度指标，值得长期看。

其他偏见（偏爱长回答、偏袒同门模型）在本系统不适用，见第一节。

## 六、陪审团（多模型交叉）：什么时候值得

用多个模型各打各的再综合，业界叫 panel of judges / LLM jury，比单裁判更稳、能抵消单个模型的偏见。已有的"多模型交叉验证"做法就是它的手工版，方向对。

**值得用的场景**：模板 B 的转人工判定（这一步错了代价最大）。

**不值得的场景**：主评估（精确匹配，压根不用裁判）、扩题库（错了成本极低，人扫一眼就行）。

聚合方式：二元判定用多数票；如果偏保守，改成"任一裁判判'没有'就转人工"——召回更高，误转更多，按业务容忍度选。

## 七、明确不要做的事

以下都是为生成式系统设计的，套到本系统上是纯浪费：

- ❌ 把回答拆成一条条断言、逐条找依据（答案是固定文本，无断言可拆）
- ❌ 把合规做成运行时闸门（写答案库时人工过一遍即可，一次性永久生效）
- ❌ 检索质量、生成质量分开归因（没有生成环节）
- ❌ 给主评估做裁判校准（精确匹配不需要裁判）
- ❌ 长度归一化、长度偏好检测（长度由答案库决定）

**一个闸门不需要修到完美。** 主保险已经上在答案库上了，裁判只需要能看出这版比上版好还是差。

## 八、落地顺序

1. [ ] 从线上真实提问里抽 100-200 条，标注正确答案编号 → 形成题库 v1
2. [ ] 跑基线：同一版本重跑两次，记录波动范围
3. [ ] 出三个数：选对率、该转人工却硬答、易混淆答案对 Top 10
4. [ ] 用模板 A 给核心题扩同义说法，测同题不同问法是否稳定
5. [ ] 按混淆对改答案库（合并 / 拆分 / 补说法）——这一步收益最大
6. [ ] 用模板 B 专测转人工边界，必要时上多模型
7. [ ] 只有当判定要驱动自动化动作时，才做第五节的校准
